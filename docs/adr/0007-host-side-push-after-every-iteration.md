# Host-side `git push` after every working-agent iteration

Tide pushes the feature branch to `origin` from the host after every working-agent iteration that produced commits, regardless of the iteration's classification (DONE, BLOCKED, or agent-FAIL) and including the catch path that handles a thrown sandcastle iteration. Push failures are `log.warn`-and-continue: the queue does not abort, no Linear state is mutated, and no label flips. The host-side push that previously lived in the PR-submission tail step is removed — by the time PR submission runs, every commit on the branch is already on origin.

## Considered

- **Push only at the end of the run, in the PR-submission tail step.** The previous behaviour. Cheapest in network calls and trivially correct when nothing goes wrong, but every commit between the first iteration and the tail is stranded on the host's worktree. If the queue aborts on an infra failure, every sub-issue BLOCKS, the user's machine crashes, or the worktree is deleted between iterations, the agent's work never reaches origin and there is no way for a human to pick it up. Rejected: the cost we pay is "user reruns potentially hours of work"; per-iteration push is a few seconds.
- **Sandbox-side push.** Have the working agent itself `git push` at the end of each iteration. Mirrors how the agent already runs `git commit`. Rejected on two grounds: (1) it widens the credential surface inside the sandbox (the agent already has `GH_TOKEN` for `gh pr create` per ADR-0003, but pushing is now a per-iteration concern, not a per-run one — making this a host responsibility matches ADR-0005's host-driven state pattern); (2) it makes push failure entangled with iteration failure, where today push failure is cleanly recoverable and the iteration result is unaffected.
- **Push only on success (DONE + commits).** Skip pushing on BLOCKED / agent-FAIL. Rejected: BLOCKED and agent-FAIL iterations frequently produce real, salvageable partial commits — a human reviewing a `ready-for-human` flip can only build on those commits if they are on origin. The whole point of per-iteration push is "partial work survives" and gating it on success defeats that.
- **Abort the queue on push failure.** Treat push failure as an infra failure, like a Linear write that fails. Rejected: push failures are commonly transient (network blip, ephemeral remote rejection) and the next iteration's push naturally carries forward the previously-missed commits. Aborting on a transient failure forces a re-run of the queue that the next push would have fixed for free.
- **Retry / backoff on push failure.** Some bounded retry inside `runIssueQueue`. Rejected: warn-and-continue is functionally equivalent — the next iteration's push _is_ the retry. Adding explicit backoff inside the runner duplicates a mechanism the per-iteration loop already provides.
- **Force-push semantics (`--force-with-lease`).** Rejected as out of scope: the working-agent prompt mandates a single forward-only commit per iteration, so the branch on origin is always a strict prefix of the local branch. A plain `git push -u` is sufficient; `-u` sets upstream on the first push and is a harmless no-op afterwards.

## Consequences

The runner's per-iteration loop in `runIssueQueue` calls `git push -u origin <branch>` on the host after the working-agent's `sandbox.run(...)` returns, gated on `SandboxRunResult.commits.length > 0`. The same call fires from the catch path that handles a thrown iteration; gating there is unnecessary because commits-on-disk are independent of the thrown result, and `git push` with no new commits is a no-op. The push fires _before_ any Linear state mutation (transition to Done, label flip, comment) so a human inspecting Linear after the fact can trust that any commit referenced in a sub-issue's timeline is already on origin.

`RunIssueQueueOptions` grows a `ShellRunner` test seam mirroring the one already on `RunPrSubmissionOptions`: `(cmd, args, cwd) => Promise<{exitCode, stdout, stderr}>`. Tests inject a fake to exercise the success path, the empty-commits skip, the throw-then-push path, and the push-fails-warn-and-continue path without invoking real `git`.

`runPrSubmission` no longer pushes — its first step is now the PR-creation iteration. Success is still verified host-side via `gh pr list --head <branch>`. The `runPrSubmission` tests covering "throws when git push fails" are removed because the surface they covered no longer exists; the same code path is exercised by the runner's push tests.

Per-iteration push status is not surfaced in the post-run summary or end-of-run warnings in this slice. A follow-up may add a "your final iteration's push didn't land — your most recent work is not on origin" warning if that turns out to matter in practice.
