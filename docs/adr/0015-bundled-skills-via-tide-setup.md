# Bundled skills installed by `tide setup` into `.claude/skills/`

> Status: **supersedes the file-scaffolding portion of `tide init`** (which is removed). ADR-0012's repo-prefix-writing responsibility moves with the skills from the dotfiles repo into tide's `src/cli/setup-templates/claude-skills/`; the fetch-side filter contract is unchanged.

Tide ships three Linear-flow skills (`tide-to-prd`, `tide-to-issues`, `tide-triage`) embedded in the binary at `src/cli/setup-templates/claude-skills/`. `tide setup` writes them into the consuming repo at `<repoRoot>/.claude/skills/tide-{to-prd,to-issues,triage}/`, always overwriting (silent if bytes match, logged path on change). `tide init` is removed; `tide setup` is the single idempotent setup command, absorbing both the prior `.tide/` scaffolding step (skip-if-exists) and the new bundled-skill writes (always-overwrite). The generated skill directories are committed to the consuming repo, not gitignored — so a fresh checkout has the skills without running `tide setup`, and updates ship as reviewable diffs in the PR that bumps tide's version. The dotfiles-side `linear-{to-prd,to-issues,triage}` skills are deleted; the new tide-bundled ones replace them outright.

## Considered

- **Real Claude Code plugin namespace (`/tide:to-prd` invoked as `tide:to-prd`).** Rejected on the discovery-mechanism asymmetry: Claude Code does not auto-discover project-level plugins. Plugins live at user scope (installed via `/plugin install` or a marketplace; layout is `.claude-plugin/plugin.json` + `skills/<name>/SKILL.md` at the plugin root). Getting a literal `tide:` prefix would require either (a) a one-time `/plugin install <repoPath>` step after `tide setup` — chips at the "no extra steps" requirement and means a fresh clone is silently broken until the user remembers it — or (b) shipping tide-as-a-globally-installed-plugin and decoupling skills from the per-repo `tide setup` — which means a fresh box without the global install gets no skills, exactly the friction we're avoiding. The hyphen prefix (`/tide-to-prd`) achieves the same visual grouping and autocomplete narrowing with zero bootstrap cost, since `.claude/skills/` is the one project-scoped location Claude Code auto-discovers.

- **Gitignore the bundled skill dirs.** Rejected: cloning the repo without running `tide setup` leaves the skills invisible to humans browsing the repo (or on GitHub) and to AI agents reading the repo cold — defeating discoverability and onboarding. With them committed, `tide setup` is a no-op when bytes already match, so committed-and-current repos see zero diff churn; updates only land when tide ships an actual change, and the diff is review-able in the PR that bumps tide's version. Treating the bundled-skill bytes as a build artefact (gitignored, regenerated locally) would also mean the consuming repo's git history doesn't record what skills it was using on a given day — a small but real loss of repro-ability.

- **Keep `tide init` and `tide setup` separate, with init owning files and setup owning Linear/bridge.** Rejected: the bifurcation was useful when "files" meant only `.tide/` scaffolding (skip-if-exists, user-edits-after-creation). Adding tide-owned skill files (always-overwrite) under the same command surface lets one command express the whole "make this repo tide-ready" intent. The two file categories live under one `tide setup` umbrella with different overwrite policies — `.tide/*` keeps skip-if-exists semantics (`config.ts` and `prompt.md` are user-edited after first creation); `.claude/skills/tide-*/` gets always-overwrite-silent-if-identical-log-on-change. One `tide setup` call handles bridge → env/config load → Linear labels + state → `.tide/` scaffold → bundled skills, with each step's failure isolated from the others' (matching today's parallel label/state error reporting).

- **Doctor checks for skill drift.** Rejected: `tide doctor` would have to flag every editor session as a drift warning, since any in-progress edit to a bundled skill differs from the embedded version. Drift gets fixed by running `tide setup`, which the user is going to do anyway when they want the bundled version back. The bridge classifier exists in doctor because a broken bridge silently breaks `tide run` at the worktree-collision check; drifted skills don't break anything — they just mean the user's local copy is ahead of (or behind) the version tide would write.

- **Always overwrite, but prompt before clobbering hand-edits.** Rejected: adds a TTY interaction and a flag for non-interactive runs (CI / scripted setups). The user signed up for "re-run to override" explicitly. If a user wants to fork a bundled skill, they can copy it to a different name (`my-to-prd`) under `.claude/skills/`, and tide leaves that one alone — the always-overwrite scope is bounded to the `tide-*/` namespace.

- **Source layout: `skills/` at repo root, parallel to `src/`.** Rejected in favour of `src/cli/setup-templates/{tide,claude-skills}/`. The `setup-templates/` parent mirrors the runtime tree (`.tide/` and `.claude/skills/` as siblings under the consuming repo's root) and keeps all setup-time-embedded files under one parent, parallel to today's `src/cli/init-templates/` (which is renamed and absorbed). A repo-root `skills/` would split the source-of-truth across two trees and require the build step to remember to bundle a non-`src/` directory.

- **Keep the dotfiles-side `linear-{to-prd,to-issues,triage}` skills as a generic Linear-flow stack, decoupled from tide.** Rejected: the existing skills are already so tide-coupled (hard-stop on missing `.tide/config.ts`, repo-prefix writing per ADR-0012, the `prd` label vocabulary per ADR-0002, the three-state Linear lifecycle) that calling them "Linear skills" was always slightly wrong — they're tide-on-Linear skills. Maintaining a generic-Linear-flow fork is a real product decision (do we want one?) and outside this move's scope. Deleting outright keeps one source of truth.

## Consequences

`src/cli/init.ts`, `src/cli/init.test.ts`, and `src/cli/init-templates/` are deleted. `src/cli/setup.ts` absorbs the file-writing logic; the source files move under `src/cli/setup-templates/{tide,claude-skills}/`, with `tide/` holding the prior init scaffolding and `claude-skills/tide-{to-prd,to-issues,triage}/` holding the bundled skill bodies. The setup output extends the existing created/already-present unified summary with skill writes folded in — a write that changed bytes lands in `created`, a write that was a no-op lands in `existing`, matching the existing label/state report shape.

The rewritten skill bodies update three things from their dotfiles ancestors: (1) frontmatter `name:` to `tide-{to-prd,to-issues,triage}`, (2) cross-skill prose references (`linear-to-issues` → `tide-to-issues` etc.) and the `tide init` → `tide setup` rename in their hard-stop error strings, (3) the `linear-to-issues` description loses its historical "merged Linear flavor of `to-issues` + `to-issues-native`…" preamble. The `.tide/config.ts` hard-stop guard at the top of each skill is preserved — cheap defence against a user who deletes `.tide/` after `tide setup` ran.

Consumers commit the generated `.claude/skills/tide-*/` directories. Each tide release that touches a bundled skill body produces a diff in every consuming repo on the next `tide setup` run; the diff is reviewable in the PR that bumps tide's version. README and `tide --help` lose `tide init` from their command tables.

The dotfiles repo's `linear-{to-prd,to-issues,triage}/` directories under `dotfiles/agents/skills/` are deleted, along with any references in `dotfiles/agents/skills/linear-flow.md`. This is a separate commit in the dotfiles repo, not part of the tide PR.
