# Two-layer worktree, sandcastle `merge-to-head` per iteration, and the Branch override

> Status: **partially supersedes ADR-0005** (the "reusable sandbox" runtime portion — `createSandbox` once per `tide run` + `sandbox.run(...)` per iteration) and **partially supersedes ADR-0006** (the single-`branch`-strategy portion). ADR-0005's "host-driven Linear writes" half stands. ADR-0006's PR↔root linkage via branch-name match stands on the non-override path; its no-magic-word stance stands on both paths. ADR-0007 (host-side push from `repoRoot`) and ADR-0009 (host-driven _In Review_ hand-off) are unaffected.

Tide now operates two layers of git worktree per `tide run`. A long-lived **Feature worktree** owned by tide rides the picked **PRD**'s or **Standalone Issue**'s Linear-auto-generated `branchName` (or, when the user takes the **Branch override**, their currently-checked-out branch); it is created at the top of `tide run` via sandcastle's `createWorktree({ branchStrategy: { type: 'branch', branch, baseBranch }, cwd: repoRoot })`, persists across runs, and is never closed by tide. Beneath it, sandcastle creates an ephemeral **Iteration worktree** per agent invocation under the `merge-to-head` strategy: each `sandcastle.run({ branchStrategy: 'merge-to-head', cwd: featureWorktreePath, sandbox: docker(), ... })` call spins up a temp branch + worktree + container, runs the agent, merges the temp branch into the **Feature worktree**'s feature branch on sandbox close, and tears everything down. The summarizer (when BLOCKED / agent-FAIL fires) is a separate `sandcastle.run(...)` call. PR submission is a single `sandcastle.run({ branchStrategy: 'head', cwd: featureWorktreePath, ... })` — direct execution in the **Feature worktree**, no per-call worktree, no merge step.

The **Branch override** replaces the prior hard pre-flight gate that errored when the user invoked `tide run` from the Linear `branchName`. After the user picks a root, if their current branch differs from the picked root's `branchName`, tide renders a clack `select` between "use Linear's `<branchName>`" (default) and "use your current `<currentBranch>`". The chosen branch becomes the **Feature worktree**'s branch. No notion of "base branches" lives in `.tide/config.ts`; the prompt is the user's only escape hatch.

Tide's prompts no longer reference sandcastle's built-in `{{SOURCE_BRANCH}}` / `{{TARGET_BRANCH}}` placeholders — those are leaky names whose meanings flip between the `branch` and `merge-to-head` strategies. Tide passes its own domain-aligned `{{FEATURE_BRANCH}}` (the **Feature worktree**'s branch) and `{{BASE_BRANCH}}` (the user's PR target, captured at `tide run` startup) via `promptArgs`.

## Considered

- **Status quo: single shared worktree under sandcastle's `branch` strategy (ADR-0005 / ADR-0006 runtime).** Rejected on two grounds. (1) **Iteration isolation**: an agent that scribbles dirty state into the shared worktree leaves residue the next iteration inherits. With per-iteration worktrees forked from the **Feature worktree**'s tip, residue gets discarded with the temp worktree at sandbox close. (2) **Live-review of the feature branch**: the user wanted to inspect the feature branch (or `git diff <base>..<feature>`) in another terminal while `tide run` is going, without seeing in-flight WIP from the currently-running iteration. Single-shared-worktree always shows WIP; the two-layer model only commits to the **Feature worktree** at iteration close, so the feature branch is "completed iterations only" between iterations.

- **Tide-driven merge orchestration to preserve the BLOCKED isolation goal.** Sandcastle's `merge-to-head` merges the temp branch unconditionally when it has any new commits — DONE, BLOCKED, and agent-FAIL all merge. The "live review only sees completed work" goal partially leaks for BLOCKED iterations. The alternative is for tide to manually `git worktree add` the **Iteration worktree**, run `createSandbox` with `branchStrategy: 'branch'` on a temp branch, classify the outcome, and merge-or-discard host-side (DONE → merge; BLOCKED / FAIL → preserve temp branch + worktree for human inspection, never merge). Rejected: the user explicitly accepted the BLOCKED-leak — they don't need to view a failed worktree's state — and accepting the leak means sandcastle owns the merge step instead of tide reimplementing it. The cost is BLOCKED iterations land partial commits on the feature branch (same as today's behaviour, no regression); the win is ~30 lines of merge-orchestration code we never write.

- **Preserve the Reusable sandbox per-iteration via tide-managed merge-to-head.** Same shape as the previous alternative but motivated by saving container spin-ups: tide creates one container + one **Iteration worktree** per iteration, runs the working agent and (on BLOCKED / FAIL) the summarizer in it, then host-side merges. Rejected: container spin-up on a cached image is seconds, not minutes, and the doubling of spin-ups only fires on BLOCKED / FAIL — the rare path. The cost of preserving Reusable sandbox is reimplementing sandcastle's merge step in tide and accepting the maintenance burden of staying aligned with sandcastle's edge cases (FF vs merge-commit when the feature branch has moved, dirty-worktree handling, temp-branch deletion). Dropping Reusable sandbox simplifies the runner code, deletes a CONTEXT.md term, and lets sandcastle own the merge step.

- **Reintroduce `Fixes <linear-id>` in the PR body when the override is taken.** Under the override, the PR's head ref is not the Linear-auto-generated `branchName`, so Linear's GitHub integration cannot match the PR back to the root for the merge-driven _In Review_ → _Done_ transition (ADR-0009). A magic-word carve-out — `Fixes <linear-id>` _only_ when the override is taken — would restore the auto-transition without violating ADR-0006's "no double-driving" concern (the branch name doesn't drive on the override path; `Fixes` would be the sole mechanism, not a duplicate). Rejected: ADR-0009 explicitly reaffirms ADR-0006's no-magic-word stance, the override is the escape-hatch / rare path by design, the body-clutter concern still applies, and "PRs sometimes have `Fixes`, sometimes don't, depending on a branch heuristic" makes the PR body shape less predictable. The user transitions the root manually after merge on the override path; tide's existing no-merge warning at end-of-run is extended to surface this case.

- **Hardcoded base-branch list (`{main, master, dev, develop}`) or configurable `baseBranches` in `.tide/config.ts` to gate the override prompt.** Rejected. Hardcoding is brittle across repos with non-default conventions. A configurable list is the "right" answer in 6 months once we have evidence we need it; today it adds config surface for a problem we don't have. The chosen rule — "always prompt when `currentBranch !== picked.branchName`, default = use Linear's" — implements the user's stated escape-hatch goal exactly, with one extra clack confirm before the existing pre-flight summary, and the default preserves the hit-Enter habit for users running from main / dev / etc.

- **Confirm-style override prompt (`Use current branch as the feature branch? (y/N)`) instead of select-style.** Rejected: the framing "do you want to override?" centres the prompt on the override concept, which the user has to know about. The select-style framing — two named options, "Linear's `<X>`" and "your current `<Y>`" — collapses the question to "pick the feature branch", which is the actual decision being made. Default-cursor on Linear's branch preserves hit-Enter ergonomics.

- **Use sandcastle's built-in `{{SOURCE_BRANCH}}` / `{{TARGET_BRANCH}}` placeholders in tide's prompts.** Rejected: their meaning flips between strategies. Under the legacy `branch` strategy: `SOURCE_BRANCH = explicit branch (= feature branch)`, `TARGET_BRANCH = host current branch (= user's PR base)`. Under `merge-to-head` with `cwd: featureWorktreePath`: `SOURCE_BRANCH = sandcastle-generated temp branch` (an implementation detail the agent shouldn't see), `TARGET_BRANCH = host current branch in cwd (= feature branch)`. Reusing the same placeholder names with flipped meanings is a footgun for anyone reading both old and new prompts. Tide-supplied `{{FEATURE_BRANCH}}` and `{{BASE_BRANCH}}` decouple tide's prompt vocabulary from sandcastle's internals and survive any future sandcastle change to the built-ins.

- **Per-run Feature worktree lifecycle (create at top of `tide run`, tear down at end).** Rejected. The branch ref state we'd want to keep across runs (commits already pushed to origin, prior iteration history) is repo-shared, not directory-shared, so tearing down the worktree directory only reclaims disk while leaving the branch ref untouched — meaning the next run recreates the same worktree against the same branch with the same prior-iteration history. Persistent matches today's behaviour (sandcastle's `WorktreeManager.create` already reuses managed worktrees on branch collision) and avoids busywork. Disk-reclamation is a separable concern handled by a future `tide cleanup` command or auto-cleanup-on-PR-merge ADR.

- **Move the **Feature worktree** to a tide-specific path (`<repoRoot>/.tide/feature-worktrees/<branch>/`).** Rejected. The on-disk topology under `.tide/worktrees/<feature>/` already exists from prior runs (sandcastle's path scheme via the **Sandcastle bridge**), and moving it would orphan those existing worktrees + require a `tide doctor` migration. The "self-documenting topology" benefit (separating feature from iteration via different parent dir names) is small — anyone reading the path needs to know two layers exist regardless. Staying at `.tide/worktrees/<branch>/` inherits sandcastle's collision-detection / `pruneStale` / "reuse if managed and clean" logic for free.

- **PR submission stays at `createSandbox({ branch: feature, baseBranch: userBase, cwd: repoRoot })`.** Rejected. Sandcastle's collision detector reuses the **Feature worktree** (clean), so it functionally works, but two callers (the runner and PR submission) reach for the same on-disk worktree by different cwd paths — a coupling that compounds with every future change. Running PR submission inside the **Feature worktree** with `branchStrategy: 'head'` (no new worktree, no merge step) keeps "every sandcastle invocation under `tide run` has `cwd: featureWorktreePath`" as a uniform rule.

- **Pure host-side `gh pr create` with a tide-rendered body (no sandbox, no agent).** Rejected as out of scope. The agent-authored PR body — the six-section emoji template responding to the specific diff (ADR-0001) — is the PR submission's main user-visible work, and removing it is a separable change that warrants its own ADR. The current decision is the smallest structural shift that delivers the iteration-isolation + live-review goals.

## Consequences

The runner (`src/runner/index.ts`) loses the top-of-run `createSandbox(...)` + reused `sandbox.run(...)` shape (per ADR-0005's runtime portion). It now calls `sandcastle.run({ branchStrategy: 'merge-to-head', cwd: featureWorktreePath, sandbox: docker(), ... })` per working-agent iteration, plus a separate `sandcastle.run(...)` for the summarizer on BLOCKED / agent-FAIL. Each call spins up its own container + **Iteration worktree** + (for the working agent) the merge step at sandbox close. The summarizer's branch strategy is non-load-bearing — `merge-to-head` is fine (no commits → merge is a no-op); `head` would also work.

The CLI orchestration layer (`src/cli/run.ts`) gains a **Branch override** step between `pickRoot` and the existing pre-flight summary. The override compares `currentBranch` (from `resolveBaseBranch`) to `picked.branchName`; when they match, no prompt fires. When they differ, a clack `select` between Linear's branch (default) and the user's current branch determines the **Feature worktree**'s branch. The today's `branchName === baseBranch → error` gate at `src/cli/run.ts:395` is removed — the override path makes "running from the feature branch" a legitimate state, not a misuse.

The **Feature worktree** is created in `runQueueAfterPick` (`src/cli/run.ts`) after the override resolves and after the pre-flight confirms succeed, via `sandcastle.createWorktree({ branchStrategy: { type: 'branch', branch: featureBranch, baseBranch: userBaseBranch }, cwd: repoRoot })`. The returned `Worktree` handle's `worktreePath` is threaded through `runIssueQueue` and `runPrSubmission` as the `cwd` for every sandcastle call. Tide never calls `worktree.close()` (close removes the directory; we want persistent). The handle is GC'd at process exit.

Each prompt template that references branch names switches from sandcastle's built-ins to tide-supplied custom keys. Files touched: `.tide/prompt.md`, `.tide/prompt-standalone.md`, `src/cli/init-templates/prompt.md`, `src/cli/init-templates/prompt-standalone.md`, `src/pr-submission/index.ts`'s inline `PR_PROMPT_TEMPLATE`, plus `src/prompt-args/index.ts` (`buildPromptArgs` adds `FEATURE_BRANCH` and `BASE_BRANCH`) and `src/pr-submission/index.ts`'s `buildPrPromptArgs` (same two keys). Tests covering prompt rendering update to assert the new keys. The `git log <base>..<feature> --oneline` shell-expression in the working-agent template uses `{{BASE_BRANCH}}..{{FEATURE_BRANCH}}` instead of the previous `{{TARGET_BRANCH}}..HEAD` — this is functionally correct under both strategies (under `branch` it's identical; under `merge-to-head` it now references the **Feature worktree**'s branch, which is the agent's HEAD-equivalent semantically).

The single-commit-per-iteration contract in the working-agent prompt is unchanged. Per-commit `ref <linear-id>` prefixes (ADR-0006's **Commit reference**) flow through sandcastle's FF merge unchanged: an agent commit on the temp branch with message `ref MEC-X: <subject>` becomes a commit on the **Feature worktree**'s feature branch with the same message after FF. The PR title's `[<linear-id>] <root-title>` (ADR-0013) is unaffected.

ADR-0006's PR↔root linkage via branch-name match is preserved on the non-override path. On the override path, the PR's head ref is the user's current branch, not Linear's `branchName`, so Linear's GitHub integration cannot match the PR back to the root and the merge-driven _In Review_ → _Done_ transition does not fire. Tide's host-driven _Triage_ → _In Progress_ → _In Review_ chain (ADR-0009) is branch-name-independent and fires on both paths. Tide's existing no-merge warning at end-of-run is extended to flag the override-induced "won't auto-transition on merge" case so the user transitions the root manually in Linear after merge.

ADR-0007's host-side push from `repoRoot` is unchanged — `git push -u origin <branch>` works from any worktree of the same repo because branch refs are repo-shared. Push fires after every working-agent iteration that produced commits, gated on `SandboxRunResult.commits.length > 0` from the per-iteration `sandcastle.run(...)` return (the merge already fired by this point, so commits land on the **Feature worktree**'s feature branch and `repoRoot`'s view of that branch is automatically current).

The **Sandcastle bridge** at `<repoRoot>/.sandcastle` → `.tide` is unchanged. The **Feature worktree** gets its own real `.sandcastle/` directory inside it (sandcastle's `cwd: featureWorktreePath` writes `.sandcastle/worktrees/<temp>` and `.sandcastle/logs/...` under the **Feature worktree**) — that's sandcastle's working directory, not bridged. `classifyBridge` only inspects the top-level repo's `.sandcastle`; the in-Feature-worktree real directory does not break it.

Container spin-up cost grows from one-per-`tide run` to one-per-agent-invocation. On a cached docker image this is seconds per spin-up; for a 5-iteration PRD with no BLOCKED / FAIL it adds roughly four extra spin-ups vs the prior model. BLOCKED / FAIL doubles the spin-up count for that iteration (working + summarizer each get their own container).

The **Reusable sandbox** term is removed from CONTEXT.md. Anyone reading older docs / ADRs that mention it should map it to "the prior pre-merge-to-head runtime; no longer applicable."

Migration: zero. The on-disk path stays at `<repoRoot>/.tide/worktrees/<sanitized-feature-branch>/`. Existing managed worktrees from prior runs are reused via sandcastle's `WorktreeManager.create` collision detection on the next `tide run`. The flagged ambiguity #3 in CONTEXT.md (about preferring sandcastle's built-in placeholder names) is removed in the same change.

Edge case (pre-existing, not introduced by this ADR): `tide run` invoked from inside a tide-managed **Feature worktree** would have `discoverRepoRoot` return the **Feature worktree** path instead of the user's main checkout, causing sandcastle to layer another worktree under it. This was already broken under the prior single-worktree model and is not worsened here. A follow-up can add a `git rev-parse --git-common-dir` walk-up in `discoverRepoRoot` to detect "I'm inside a worktree" and resolve to the canonical main checkout.

Cleanup of stale **Feature worktrees** (after their PR has merged + the branch has been deleted upstream) is out of scope. Today's `tide doctor` does not inventory worktrees; that stays. A future ADR can introduce auto-cleanup-on-PR-merge or a `tide cleanup` command.
