# In Review hand-off for PRDs and Standalone Issues; Sub-issues stay host-driven to Done

The runnable units split into two lifecycles. **Sub-issues** keep their existing host-driven path: each iteration's start transitions the Sub-issue to _In Progress_, and a DONE signal with commits transitions it to _Done_, mid-run, so the user sees per-iteration progress in Linear's UI. **PRDs** and **Standalone Issues** — the parents that map 1:1 to a PR — gain a new stop. After `tide run` finishes a clean queue and successfully opens a PR, the CLI orchestration layer transitions the parent to a new workflow state, **_In Review_**. Linear's GitHub integration then drives the final _In Review_ → _Done_ transition when the PR merges. The `In Review` state name is hardcoded; `tide setup` provisions it idempotently between _In Progress_ and _Done_, and `tide doctor` / `tide run` hard-fail at preflight if it cannot be resolved on the team.

## Considered

- **Status quo: PRDs and Standalone Issues transition to _Done_ at end-of-clean-queue, like Sub-issues.** Rejected: this is the [PER-51](https://linear.app/meca-therapies/issue/PER-51/dotfiles-update-linear-triage-skill-to-move-out-of-triage-state-when) failure mode. The agent's `<promise>DONE</promise>` is "I think I'm done," not "the code shipped" — and on a Standalone Issue with no Sub-issues the parent flips to Done the moment the agent commits, before any human has seen the PR (or before the PR even exists). Conflating "agent finished" with "shipped" misrepresents the parent's state and trains users to ignore the Done column.
- **Symmetric: route Sub-issues through _In Review_ too, so every runnable unit gets the same hand-off.** Rejected: a long PRD with many Sub-issues would appear stuck for hours — every Sub-issue sitting at _In Review_ waiting on a single PR-merge transition at the end. The whole point of mid-run host-driven transitions on Sub-issues (per ADR-0005) is real-time progress visibility on the long-running case. The asymmetry is the feature.
- **Auto-transition the parent to _Done_ at end-of-clean-queue (without an _In Review_ stop).** This is ADR-0006's third rejected alternative. It still races real PR-merge — tide marks the parent _Done_ before the code lands. Rejected on the same grounds; introducing an _In Review_ stop fixes the race because _In Review_ does not claim "shipped," it claims "ready for review."
- **Configurable state name via `.tide/config.ts`.** Rejected: the value-add is small (the state name "In Review" is Linear's standard), the config surface is real, and a hardcoded contract — "you have a state called `In Review`, or you let `tide setup` create it" — is what allows preflight to be a hard failure with an unambiguous remediation. Future motivation can re-open the question.
- **Soft-fallback to _Done_ when _In Review_ cannot be resolved.** Rejected: a silent fallback re-introduces exactly the [PER-51](https://linear.app/meca-therapies/issue/PER-51/dotfiles-update-linear-triage-skill-to-move-out-of-triage-state-when) misrepresentation this ADR exists to fix. Preflight failures in `tide doctor` and at `tide run` startup point the user at `tide setup`; there is no path that silently degrades.
- **Auto-retry on a failed In Review transition.** Rejected: the PR is already open and the queue's earlier Linear writes are already correct. A retry loop adds complexity for a transition the user can do by hand in seconds. The failure path emits a warning naming the parent and tells the user to transition manually; the PR is preserved.
- **Place the In Review hook inside the runner, alongside the per-iteration transitions.** Rejected: the trigger predicate depends on artefacts the runner doesn't own — the PR-submission step's outcome (opened? skipped?) and the queue-result aggregate (clean? aborted?). Putting the hook in the CLI orchestration layer lets the runner stay focused on per-Sub-issue iteration work, mirroring the layering already used for the PR-submission tail step.

## Consequences

The asymmetry is deliberate and load-bearing: **Sub-issues** transition to _Done_ host-side at iteration end so a long PRD shows live progress, while **PRDs** and **Standalone Issues** transition to _In Review_ post-submission so the parent's state stays honest about whether code has shipped. Sub-issues never transit through _In Review_; their lifecycle is _In Progress_ → _Done_. Parents lifecycle is **Triage → In Progress → In Review → Done**, with tide owning the first three transitions and Linear's GitHub integration owning the merge-driven last one.

The In Review transition fires only when _all_ of the following hold: the queue completed at least one unit (`completed > 0`), nothing flipped to `ready-for-human` (`flipped === 0`), the queue did not abort (`abortedAt === undefined`), and PR submission returned successfully with a PR URL. Any other combination skips the transition. PRD roots get a warning ("not transitioned to In Review — queue had flipped or incomplete sub-issues") at end-of-run; Standalone roots fall through to the existing `ready-for-human` warning when the iteration produced no commits. Standalone roots that complete cleanly but skip PR submission stay at _In Progress_; tide's existing no-PR warning covers that case.

A failed In Review transition is logged as a warning and does not unwind. The PR stays open, the queue's existing per-Sub-issue Linear writes (transitions, label flips, comments) stay applied, and `tide run` exits zero. The user transitions the parent manually. This matches how tide treats other late-run, post-success Linear writes: don't undo earlier work to compensate for a transient failure on a downstream write.

`tide setup` provisions the `In Review` workflow state idempotently. The state's `position` is computed strictly between the lowest-`position` `started` state (assumed _In Progress_) and the lowest-`position` `completed` state (assumed _Done_), so it reads naturally left-to-right in Linear's UI between _In Progress_ and _Done_. Re-running `tide setup` on a team that already has _In Review_ is a no-op — no duplicate state, no position shift. `tide doctor` and `tide run` both call the preflight check; failure points the user at `tide setup`.

The runner's end-of-iteration code path branches on the queued unit's root kind: PRD root → existing transition to _Done_ (no change); Standalone root → skip the host-side _Done_ transition. The CLI orchestration's post-submission hook fires for both kinds — the In Review hand-off is the same whether the parent is a PRD or a Standalone Issue.

This ADR partially supersedes ADR-0005 and ADR-0006. ADR-0005's "DONE → completed" conclusion remains correct for **Sub-issues**; the Linear writes are still host-driven (the host owns every transition tide makes) but the target state for **PRDs** and **Standalone Issues** is now _In Review_, not _Done_. ADR-0006's single-PR-per-PRD model and its no-magic-word stance are unchanged; only its specific rejection of "tide auto-transitions the parent at end-of-clean-queue" shifts at the parent level — adopted in a refined form (transition to _In Review_, not _Done_; gated on PR-opened, not end-of-clean-queue alone) that does not race the merge transition.
