# PR target branch resolved from `origin/HEAD` with user confirmation

> Status: **partially supersedes ADR-0014** (the "{{BASE_BRANCH}} captured at `tide run` startup" decision in its Branch override section). ADR-0014's two-layer-worktree, `merge-to-head`-per-iteration, and Branch override decisions stand. ADR-0006's PR↔root branch-name linkage and no-magic-word stance stand. ADR-0007's host-side push and ADR-0009's host-driven _In Review_ hand-off are unaffected.

The **PR target branch** (the branch the eventual PR merges into; surfaced as `{{BASE_BRANCH}}` in tide-owned prompts and passed to `gh pr create --base`) is now resolved from `origin/HEAD` rather than from `git rev-parse --abbrev-ref HEAD`. When the user's current branch matches `origin/HEAD` (typical: invoked from trunk), tide proceeds silently. When they differ (typical: user invoked from a hand-named feature branch on the **Branch override** path), tide prompts with `origin/HEAD` as the default and lets the user supply their own. A user-supplied override must resolve to a local ref (`git rev-parse --verify`) — tide does not auto-fetch on the user's behalf.

ADR-0014 captured one value at run startup (`resolveBaseBranch`, returning `git rev-parse --abbrev-ref HEAD`) and used it as both "current branch" (override comparison) and "PR target" ({{BASE_BRANCH}}, `gh pr create --base`, `git rev-list <base>..<feature>`). The two roles diverge exactly in the workflow the **Branch override** exists to support: a user invoking `tide run` from their hand-named feature branch and picking "current" in the override prompt got `featureBranch === baseBranch`, the rev-list gate skipped PR creation as "no commits ahead", and the override-active warning never fired (it was gated on `tail.outcome.kind === "opened"`). The override path silently produced no PR. This ADR splits the two roles: `currentBranch` (HEAD) is captured for the override decision only; the **PR target branch** is captured separately from `origin/HEAD` and exposed for user override.

## Considered

- **Status quo: keep the single-capture model and document "must invoke from trunk" as the only supported workflow.** Rejected. The user explicitly wanted "invoking from a hand-named feature branch" to be a real workflow — the **Branch override** entry in CONTEXT.md says so, and the user reaffirmed this. Forcing trunk-only invocation would close the override path's actual use case, and the existing override implementation already half-supports the feature-branch workflow (the worktree creates correctly; only the PR step silently no-ops). Documenting around the gap leaves the silent-no-PR footgun in place.

- **Configurable `baseBranch` in `.tide/config.ts`.** Rejected (again, with new evidence). ADR-0014 rejected this for being premature, and that reasoning still holds for repos that follow git's `origin/HEAD` convention — they get the right answer without any config. The remaining cases (non-default remote names, missing `origin/HEAD`, multi-trunk repos) are handled by the user-confirmation step: the user types or selects their target branch when the auto-detection isn't right. Adding config surface for the same problem prompt-confirmation already solves would duplicate mechanism without removing the prompt (someone still has to keep the config in sync if their default branch changes).

- **Always-confirm prompt, even when current branch == origin/HEAD.** Rejected. The trunk-trunk case is the dominant invocation pattern; adding a hit-Enter prompt there is friction with no upside (the user already chose to invoke from trunk; their consent is implicit in the choice of working directory). Smart-silent — confirm only when current ≠ origin/HEAD — earns the prompt's keystrokes by firing exactly when the user should be thinking about the answer.

- **Auto-fetch missing local refs (`git fetch origin <branch>` on the user's behalf when their typed branch resolves only as `origin/<branch>`).** Rejected. Adding a fetch step inside `tide run` is scope creep (tide doesn't otherwise mutate the user's repo state pre-flight), and silently proceeding with a remote-only ref invites mismatches between "what the worktree was forked from" (stale local view) and "what the PR targets" (current remote tip). Hard-failing with the explicit `git fetch && git checkout <branch>` hint keeps the failure mode predictable and one-line-fixable.

- **Compute the PR target via `git merge-base` against the picked Linear branch, or by walking the reflog.** Rejected. Both heuristics are brittle: `merge-base` against an unrelated branch picks an arbitrary common ancestor, the reflog is order-dependent, and neither survives a reset or a rebase. `origin/HEAD` is git's explicit "remote default" pointer — when set correctly, it answers the exact question we're asking; when not set, the prompt is the right escape hatch.

- **Fold the PR-target prompt into the existing Branch override prompt as a single multi-step picker.** Rejected. The two questions resolve at different times conceptually (override is "which branch the agent commits to"; PR target is "where the PR merges into") and have different default rules (override default = Linear's; PR target default = origin/HEAD). Combining them into one widget makes both harder to read and makes the silent paths (current == Linear's branchName for override, current == origin/HEAD for PR target) less obvious. They stay as two sequential prompts, each with its own silent path.

## Consequences

The CLI orchestration layer (`src/cli/run.ts`) gains a separate **PR target branch** resolution step between the **Branch override** and the existing pre-flight summary. The capture sequence is now: `currentBranch = git rev-parse --abbrev-ref HEAD` → **Branch override** decision (uses `currentBranch`, sets `featureBranch`) → `originHead = git rev-parse --abbrev-ref origin/HEAD` (best-effort; absence is non-fatal) → **PR target branch** decision (silent if `currentBranch === originHead`, otherwise prompt with `originHead` as default, accept user-typed alternative validated by `git rev-parse --verify`).

The `resolveBaseBranch` function in `src/pr-submission/index.ts` is renamed `resolveCurrentBranch` (its actual semantic: capture `git rev-parse --abbrev-ref HEAD`, fail on detached HEAD). A new `resolveOriginHead` returns the remote default branch (or `undefined` when `origin/HEAD` is unset). A new `src/pr-target/` module mirrors `src/branch-override/`'s shape (pure decision + clack UI seam) so the prompt is unit-testable without rendering UI. The `RunOptions.baseBranchShellRunner` test seam is renamed to `currentBranchShellRunner` and a new `originHeadShellRunner` seam is added.

`runQueueAfterPick` now threads two distinct values: `featureBranch` (from the override decision) and `baseBranch` (the resolved **PR target branch**). These flow independently to `createWorktree`, `runIssueQueue`, and `runPrTailStep`. The `featureBranch === baseBranch` case (rev-list gate skips) is now reachable only when the user explicitly types their feature branch as the PR target — the smart-silent path can no longer produce it.

The override-active warning at end-of-run is generalised: it fires whenever the user took the override (`featureBranch !== picked.branchName`), not just when the PR-tail outcome is `opened`. Under the conflation, the warning was suppressed on the silent-no-PR path; under the split, the silent-no-PR path is gone, but the warning logic is simplified to "if override taken, warn — regardless of PR outcome" so it's robust to future tail-outcome changes.

The base-branch local-ref validation introduces one new failure mode: a user types `dev` having only `origin/dev` locally, gets an error with the hint "run `git fetch && git checkout dev`, then re-run", and the run aborts cleanly before any Linear write. Existing failure modes (detached HEAD, malformed branch input) are preserved.

`origin/HEAD` is unset in some clones (older `git clone` invocations, certain CI setups, `git remote add origin` without a subsequent `git remote set-head`). When unset, `resolveOriginHead` returns `undefined`, the **PR target branch** prompt fires unconditionally with no default, and the user types the branch. No silent fallback to `currentBranch` — falling back would re-introduce the conflation.

CONTEXT.md adds **PR target branch** as a domain term and updates Flagged ambiguity #3 to point at it. The **Branch override** entry is updated to clarify that the override decision is independent of the PR target.

Migration: zero on disk. Behavioural change is one extra prompt step that fires only when `currentBranch !== origin/HEAD` (the override workflow). Trunk-trunk users see no UX change.
