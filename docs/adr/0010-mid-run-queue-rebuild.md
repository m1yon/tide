# Mid-run queue rebuild absorbs new Sub-issues at every iteration boundary

The runner re-fetches the picked **PRD**'s direct children from Linear at every **iteration boundary**, excludes identifiers tide has already handled this run (transitioned to _Done_ or flipped to `ready-for-human`), feeds the rest through the existing pure `buildOrderedQueue`, and continues against the rebuilt topo order. New **Sub-issues** the human added in Linear's UI mid-run are absorbed; queued-but-not-yet-run ones whose `ready-for-agent` label was removed are dropped. The runner exposes the ordered list of **processed Sub-issues** on `RunIssueQueueResult` so the PR-tail step renders the "Sub-issues addressed" block from what tide actually ran, not from the pre-flight snapshot. Standalone roots are unchanged — they have no children and no boundary.

## Considered

- **Status quo: snapshot the queue once at the top of the run.** Rejected: a long PRD-rooted run can take an hour; the user notices new work mid-run (a follow-up they spotted in the agent's commits, a bug the agent surfaced, a slice they realised was missing) and there is no way to feed it into the in-flight queue. Their only options are wait, then start a fresh `tide run` once the current one finishes; or kill the run and lose the in-flight work. Both are worse than re-polling at the boundary.
- **Lift ADR-0005 to let the agent itself create Sub-issues from inside the sandbox.** Rejected: ADR-0005 is load-bearing (the sandbox never sees `LINEAR_API_KEY`; all Linear writes are host-driven); changing that to give the working agent Sub-issue authoring rights is a much bigger surface area than the user need motivating this ADR. Scoped to human-added Sub-issues; agent-spawned Sub-issues are a separate decision if they ever land.
- **Append new arrivals to the end of the existing queue instead of a full topo rebuild.** Rejected: silently wrong when a new Sub-issue X carries a `blockedBy` pointing at a still-queued Sub-issue Y — append would run X before Y. Reusing `buildOrderedQueue` for the rebuild costs one topo-sort per boundary (microseconds) and inherits the existing closed-blocker / external-blocker / cycle handling for free.
- **Abort the run on a fresh topo error mid-run, mirroring the start-of-run abort policy.** Rejected: aborting after thirty minutes of clean queue work because the user added one malformed Sub-issue is brutal and trains the user not to touch Linear during a run — exactly the opposite of the flexibility this ADR exists to provide. Adopted instead: warn-and-skip the offending node, retry the rebuild once with it dropped, and only abort if the rebuild _still_ fails (which means the malformation is in the existing queue, not in a new arrival).
- **Abort the run on a `fetchSubIssues` API failure mid-run.** Rejected: the rebuild is a convenience, not a correctness invariant. A flaky Linear call mid-run shouldn't kill a queue that is otherwise fine. Adopted instead: warn-and-continue with the previous boundary's queue snapshot — same shape as ADR-0007's stance on `git push` failures, where the next iteration's call subsumes the missed work.
- **Soft-fall-back to the previous queue on any topo error (instead of warn-and-skip).** Rejected: silently delaying new Sub-issues until the next run is surprising — the user added a Sub-issue and tide visibly didn't notice. Warn-and-skip names the offending node out loud, so the user can fix it in Linear immediately and the rest of the rebuild proceeds.
- **Symmetric: rebuild on Standalone Issue roots too.** Rejected: a Standalone Issue is structurally a non-PRD with no children (the runner errors at selection if it has any). There is no queue to grow. Asymmetry follows from the existing root-kind asymmetry baked into `RunRoot`.
- **Reprint the full updated queue at every boundary in the runner's log output.** Rejected: noisy, and the iteration-level `Starting <id>` lines already show what tide is about to run. Adopted instead: a single `Picked up new sub-issue: <id> <title>` line per absorbed Sub-issue at the boundary it joined — same shape as the existing `Skipping <id>: ready-for-human` line.

## Consequences

The runner's loop changes shape from a `for (const ordered of orderedIssues)` over a fixed array to a stateful loop driven by a `Set<identifier>` of already-handled units plus a per-boundary call to `fetchSubIssues` + `buildOrderedQueue`. The runner gains a `fetchSubIssues` test seam (default = `linear.fetchSubIssues`) and the PRD's Linear UUID as a required option when `root.kind === "prd"`. The CLI's pre-flight queue build in `runQueueAfterPick` still runs (it owns the pre-flight UX); the runner's first boundary effectively re-derives the same queue, which is acceptable — one redundant topo per run is not a cost.

`RunIssueQueueResult` grows a `processed: OrderedIssue[]` field carrying every Sub-issue tide actually ran, in run order. The CLI's PR-tail step builds `subIssueRefs` from `result.processed` instead of the pre-flight `orderedIssues`, so the PR body's "Sub-issues addressed" block reflects the true scope of the diff. The `completed` and `flipped` counts stay on the result for log-message readability — they are derivable from `processed` but cheap to keep.

The In Review hand-off (ADR-0009) is unaffected at the predicate level: `completed > 0 && flipped === 0 && !abortedAt && pr.opened` continues to gate the transition. Absorbing more Sub-issues mid-run grows the `completed` count when they finish cleanly, which is the desired behaviour — the PRD only flips to _In Review_ when every queued unit (initial + absorbed) ran cleanly.

A topo error involving a new arrival is warn-and-skip with a single retry: tide drops the offending identifier from the candidate set, re-runs `buildOrderedQueue`, and continues if the rebuild succeeds. If the second attempt also fails, that means the malformation is in the existing queue (a previously-valid Sub-issue acquired a fresh `blockedBy` mid-run that creates a cycle with another remaining one) — tide aborts via the existing infra-failure path. A `fetchSubIssues` exception is warn-and-continue: tide logs the failure and proceeds with the previous boundary's snapshot; the next boundary's call retries naturally.

A side benefit falls out for free: removing the `ready-for-agent` label from a queued-but-not-yet-run Sub-issue mid-run pauses it (the rebuild's ready-for-agent filter omits it). The user has a no-restart way to defer work without losing the in-flight queue.
